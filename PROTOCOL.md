# Streamy signaling protocol — v1

This is the **only** thing shared between `screenshare-app/` (the Go desktop app)
and `stream-site/` (the Cloudflare Worker and the browser viewer). Neither side
imports the other; both implement this document independently.

The same file lives in both repositories. If you change it, change both, and bump
the version.

## Scope

Signaling exists **only to set up a WebRTC connection**. It carries SDP offers,
answers and ICE candidates. Video never goes through the signaling server: once
negotiation finishes, media flows directly between the host and each viewer, or
through a TURN relay when a direct path is impossible.

Consequences worth remembering:

- The worker is cheap to run because it only sees a few kilobytes per viewer.
- If the signaling server is down, existing streams keep working; only new
  viewers cannot join.
- Keyframes (PLI/FIR) are **not** part of this protocol. Those are RTCP packets
  that pion and the browser exchange directly on the media path.

## Roles

| Role | Who | Cardinality |
| --- | --- | --- |
| `host` | The Go app that is sharing a screen | Exactly one per room |
| `viewer` | A browser watching | Zero or more, up to the room limit |

## Transport

- WebSocket over TLS.
- Endpoint: `wss://<worker-host>/v1/room/<roomID>/ws`
- One text frame per message, each containing one JSON object.
- Binary frames are not used; the worker closes the connection if it sees one.
- The room ID is in the URL path only because the worker needs it to route the
  connection to the right Durable Object. It is **not** a secret.
- Credentials are **not** in the URL. They travel in the first message
  (`hello`), never in a query string, so they do not end up in access logs,
  browser history or `Referer` headers. The viewer link puts them in the URL
  *fragment* for the same reason; see [Viewer link](#viewer-link).

An `Origin` header check on the worker side is recommended: the viewer page is
the only legitimate browser origin.

## Identifiers and secrets

| Name | Format | Length | Notes |
| --- | --- | --- | --- |
| `roomID` | `base64url` without padding, from 12 random bytes | 16 chars | Public. Generated by the host. |
| `token` | `base64url` without padding, from 32 random bytes | 43 chars | **Secret.** A bearer capability: whoever has it can watch. |
| `peerID` | `base64url` without padding, from 6 random bytes | 8 chars | Assigned by the server on `welcome`. |

Rules:

- Both `roomID` and `token` are compared **exactly** and case sensitively.
- The token comparison on the server must be constant time.
- The host generates both with a cryptographically secure RNG
  (`crypto/rand`). Never reuse a room ID across sessions.
- The worker stores only the token it was given for the lifetime of the room. It
  keeps no long-term record of rooms or viewers.

## Room lifecycle

1. A host connects and sends `hello` with `role: "host"` and its `token`.
   - If the room does not exist, it is created, and the token becomes the room's
     token.
   - If the room exists and the token matches, the host reconnects (this is how
     an ICE restart or a network blip recovers) and the session continues.
   - If the room exists, the token matches, and a host is **already connected**,
     the new connection is rejected with `room-in-use`.
2. Viewers connect and send `hello` with `role: "viewer"` and the same token.
   - A wrong or missing token is rejected with `unauthorized`.
   - The worker rejects with `room-full` once the viewer limit is reached.
3. The host is told about each viewer with `peer-joined`, and each new viewer is
   told about the host with `welcome` (`hostPresent`).
4. When a peer disconnects, or sends `bye`, the others receive `peer-left`.
5. When the **host** disconnects, the room enters a grace period (default 30 s)
   so a quick restart can reclaim it. If the host does not come back, the room is
   destroyed, and every remaining viewer gets `error` with code `host-gone`
   before the socket closes with code `4001`.

Because the room's token is the only credential, a destroyed room ID can never
be reused with a stale link: a new session generates a new room ID.

## Message envelope

Every message is a JSON object with at least:

```json
{ "v": 1, "type": "<message type>" }
```

- `v` — protocol version. Always an integer. See [Versioning](#versioning).
- `type` — see the tables below.
- Unknown fields **must be ignored** by both sides. That is what makes adding a
  field a backwards-compatible change.

## Client → server messages

| `type` | Fields | Meaning |
| --- | --- | --- |
| `hello` | `role` (`"host"` \| `"viewer"`), `token`, optional `maxViewers` (host only), optional `capabilities` (object) | Must be the first message. Anything else first is `bad-message`. |
| `offer` | `sdp` (string), optional `to` (peerID) | Forwarded to the other peers, or to one peer when `to` is set. Sent by the host. |
| `answer` | `sdp` (string), optional `to` | Forwarded. Sent by a viewer. |
| `candidate` | `candidate` (string), optional `sdpMid`, optional `sdpMLineIndex`, optional `to` | Forwarded. Trickled as they are gathered. |
| `bye` | optional `reason` (string) | Graceful goodbye; the sender is disconnected after it is relayed. |
| `ping` | `t` (integer, unix milliseconds) | Keepalive. The server replies with `pong`. |

`maxViewers` in `hello` is a **request**: the server clamps it to its own hard
cap. `0` means "as many as the server allows".

`capabilities` is free-form and informational, e.g.
`{"trickleICE": true, "codec": "h264"}`. Never gate behaviour on it existing.

## Server → client messages

| `type` | Fields | Meaning |
| --- | --- | --- |
| `welcome` | `room`, `peerID`, `role`, `token` (echo of the accepted token), `hostPresent` (bool), `viewerCount` (int), `maxViewers` (int), optional `iceServers` (array) | Sent after a successful `hello`. |
| `peer-joined` | `peerID`, `role` | A viewer joined (the host is told so it can create a PeerConnection and send an `offer`). Also sent to viewers when the host appears. |
| `peer-left` | `peerID`, `role`, optional `reason` | A peer is gone. Tear down that PeerConnection. |
| `offer` / `answer` / `candidate` | Same fields as the client versions, plus `from` (peerID) | Relayed. `from` is added by the server and must not be spoofable. |
| `pong` | `t` (the value echoed from `ping`) | Keepalive reply. |
| `error` | `code`, `message`, optional `fatal` (bool, default `true`) | See below. |

`iceServers` is an optional server-supplied STUN/TURN list in WebRTC
`RTCIceServer` shape:

```json
{ "urls": ["stun:stun.l.google.com:19302"] }
{ "urls": ["turn:turn.example.com:3478"], "username": "...", "credential": "..." }
```

The clients keep their own configured servers and use `iceServers` only as an
addition (the host's config wins, because it is the one paying for TURN).

### Error codes

| `code` | Meaning | Socket |
| --- | --- | --- |
| `bad-message` | Malformed JSON, wrong `type`, or a message before `hello` | stays open |
| `unsupported-version` | `v` is missing or not `1` | closed `1002` |
| `unauthorized` | Wrong or missing token | closed `1008` |
| `room-in-use` | A host is already connected to this room | closed `1008` |
| `room-full` | Viewer limit reached | closed `1008` |
| `rate-limited` | Too many messages | closed `1008` |
| `host-gone` | The host did not come back | closed `4001` |
| `internal` | Server bug | closed `1011` |

Close codes: `1000` normal, `1002` protocol error, `1008` policy violation,
`1011` internal, `4001` host gone. Application codes start at `4000`.

## Ordering rules

1. **`hello` first.** Anything else before it is `bad-message`.
2. **The host always offers.** For every `peer-joined` with `role: "viewer"`, the
   host creates one `RTCPeerConnection`, adds the shared video track and sends an
   `offer` with `to` set to that viewer's `peerID`.
3. **One PeerConnection per viewer.** They all send the *same* encoded track;
   that is why a second viewer costs bandwidth but no extra encoding.
4. **Candidates may arrive before the offer.** Buffer them per peer and flush
   after `setRemoteDescription`. This is normal WebRTC behaviour, not an error.
5. **`peer-left` is authoritative.** Close the PeerConnection on `peer-left`,
   and also if ICE fails on its own.
6. **Ignore messages from unknown peers.** After a `peer-left`, late candidates
   can still arrive.

## Rate limiting and limits

The worker must apply, per connection:

- A cap on messages per second (start at 60) and on total ICE candidates per
  second (start at 30). Exceeding either is `rate-limited`.
- A maximum message size (start at 64 KiB) — anything larger is `bad-message`.
- A maximum room viewer count, server side (start at 20), regardless of what the
  host asked for.
- An idle timeout (start at 60 s without a `ping`/`pong` or any other message).

## Keepalive

- Either side may send `ping` with `t`; the receiver replies with `pong` and the
  same `t`.
- The server sends a `ping` after 30 s of silence and closes the socket if no
  `pong` arrives within 30 s.
- WebSocket-level ping/pong frames are *not* enough on their own: a Cloudflare
  Durable Object hibernates idle WebSockets, and lingering sockets are what keep
  a room alive.

## Viewer link

The host turns a session into a link of this shape:

```
https://<viewer-host>/#room=<roomID>&token=<token>&signal=<wss-url>
```

Everything after `#` is a fragment: it is never sent to the web host, never
logged there, and never leaked in a `Referer` header. The viewer page reads it
with `location.hash`, then connects to `<wss-url>` (defaulting to a URL baked
into `app.js` when `signal` is absent).

The token is a capability. Anyone with the link can watch, so treat the link like
a password: it is not a channel for sharing with strangers.

## Versioning

- `v` is an integer, currently `1`.
- **Additive changes** (a new optional field, a new message type that older
  peers may ignore) do **not** bump the version.
- **Breaking changes** (renaming a field, changing a meaning, removing a type)
  bump `v`. The worker then serves `/v1/...` and `/v2/...` side by side, and each
  implementation keeps the old version alive until its clients have moved.
- A client that receives a `v` it does not implement must fail loudly with
  `unsupported-version` rather than guess.

## Worked example

The host starts a session: it picks a room and a token, and displays

```
https://user.github.io/streamy/#room=k7Zf3Qn1xWp8aB2c&token=9dH...&signal=wss://streamy-signal.example.workers.dev
```

**Host connects**

```json
→ { "v": 1, "type": "hello", "role": "host", "token": "9dH...", "maxViewers": 10 }
← { "v": 1, "type": "welcome", "room": "k7Zf3Qn1xWp8aB2c", "peerID": "Hp2Kd9Qa", "role": "host",
    "token": "9dH...", "hostPresent": true, "viewerCount": 0, "maxViewers": 10 }
```

**A viewer opens the link**

```json
→ { "v": 1, "type": "hello", "role": "viewer", "token": "9dH..." }
← { "v": 1, "type": "welcome", "room": "k7Zf3Qn1xWp8aB2c", "peerID": "Vx71mQz0", "role": "viewer",
    "token": "9dH...", "hostPresent": true, "viewerCount": 1, "maxViewers": 10 }
```

The host learns about it:

```json
← { "v": 1, "type": "peer-joined", "peerID": "Vx71mQz0", "role": "viewer" }
```

**Negotiation**

```json
→ { "v": 1, "type": "offer", "to": "Vx71mQz0", "sdp": "v=0\r\no=- ..." }
← { "v": 1, "type": "offer", "from": "Hp2Kd9Qa", "sdp": "v=0\r\no=- ..." }

→ { "v": 1, "type": "answer", "to": "Hp2Kd9Qa", "sdp": "v=0\r\no=- ..." }
← { "v": 1, "type": "answer", "from": "Vx71mQz0", "sdp": "v=0\r\no=- ..." }

→ { "v": 1, "type": "candidate", "to": "Vx71mQz0", "candidate": "candidate:...", "sdpMid": "0", "sdpMLineIndex": 0 }
← { "v": 1, "type": "candidate", "from": "Hp2Kd9Qa", "candidate": "candidate:...", "sdpMid": "0", "sdpMLineIndex": 0 }
```

From here the video flows directly between the two peers. The worker sees
nothing else until someone leaves:

```json
→ { "v": 1, "type": "bye", "reason": "tab closed" }
← { "v": 1, "type": "peer-left", "peerID": "Vx71mQz0", "role": "viewer", "reason": "bye" }
```

## Implementation notes

**Go side** (`screenshare-app/internal/signal/`, phase 4). The `Signaler`
interface exists so the WebSocket implementation can be swapped for something
else later (a self-hosted server, libp2p). It should expose roughly:

```go
type Signaler interface {
    // Connect joins a room and returns the messages the pipeline must react to.
    Connect(ctx context.Context, session Session) (<-chan Message, error)
    // Send relays one negotiation message.
    Send(ctx context.Context, msg Message) error
    Close() error
}
```

**Worker side** (`stream-site/worker/`, phase 4): one Durable Object instance per
room, one WebSocket per peer. The Durable Object is the only place that knows the
room's token and its peer list, which is exactly the "one actor per room"
pattern Durable Objects exist for.

**Viewer side** (`stream-site/viewer/`, phase 6): plain HTML/JS, no build step.
It reads the fragment, connects, answers the host's offers, and shows a
`<video>` element.
